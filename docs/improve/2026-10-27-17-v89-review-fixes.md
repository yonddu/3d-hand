# 17. v89 검토 4가지 수정 (2026-10-27)

검토 기준은 v89(`fec401b`)예요. 이번 작업 커밋은 `b3ac590`, `de0172b`, `b7c64f4`, `9c47bd2`, `a92c2bf`, `e8b4358`이고 모두 main에 올렸어요. 유료 API나 서비스, NC·연구 전용 자산, 새 다운로드는 쓰지 않았어요. 새 데이터도 만들지 않았고, seed10은 채점에만 썼어요.

## 1. 모델 업데이트가 기존 사용자에게 전달되도록
**원인.** 서비스 워커가 `vendor/` 안의 파일은 "이름이 같으면 내용도 같다"고 보고 한 번 받은 파일을 계속 썼어요. 그래서 모델 파일을 교체해도 휴대폰에는 옛 모델이 남았어요.

**수정.**
- `build.mjs`: 모델 3개의 내용 해시(SHA-256 앞 10자리)를 `HMS_CONFIG.modelHash`에 적어요.
- `palmFace.js versioned()`: 모델 주소를 `파일?h=해시`로 만들어요.
- `palmFace.js fetchModel()`가 새로 생겼고, 관절 큐브 모델도 이 함수를 같이 써요.
  - 받은 바이트의 해시가 페이지가 원하는 해시와 다르면 거부해요. 그래서 앱과 모델 버전이 섞이지 않아요.
  - artifact에서는 모델을 base64 텍스트로 읽어요.
  - 로드에 실패하면 다음 호출 때 다시 시도해요.
- `sw.js model()`:
  - 바이트 해시가 `?h=`와 같을 때만 저장해요. 서버는 `?h=`를 무시하므로, 옛 탭이 새 모델 바이트를 옛 이름으로 저장하던 경로를 막았어요.
  - 파일마다 최신 2개 버전을 보관해요. 그래서 직전 버전 탭도 오프라인에서 돌아가요.
  - 옛 서비스 워커가 해시 없이 저장해 둔 사본은 지워요.
  - 새 사본을 저장한 다음에 옛 사본을 지워요.
  - 캐시 전체는 지우지 않아요.
- `build.mjs`: artifact에 사진 모델 3개(base64)와 해시를 넣었어요. 예전 artifact에는 모델이 아예 없었어요.

**테스트.** `tools/test-sw-models.cjs`를 실제 Chromium에서 돌려 14개 항목이 모두 통과했어요.
- v89 서비스 워커에서 새 서비스 워커로 넘어가는 경우
- 모델이 A, B, C로 차례로 바뀌는 릴리스
- 오프라인
- 모델이 바뀐 뒤 옛 탭이 옛 모델을 요청하는 경우
- 같은 모델을 다시 받지 않는지
- 페이지가 다른 릴리스 모델을 거부하는지
- 실패한 로드를 다시 시도하는지

## 2. 양손 검출과 정답의 1:1 매칭
**원인.** v89까지는 검출 하나가 양손 정답 모두에 붙는 경우가 있었어요. seed21에서 사진 158장, 크롭 316개가 이렇게 오염돼 있었어요.

**수정.** `tools/match-hands.mjs`로 규칙을 하나로 정했어요.
- 21개 점의 거리로 비교해요. MediaPipe의 왼손/오른손 표시는 쓰지 않아요.
- 짝은 1:1로만 정해요.
- 다른 손보다 2배 이상, 그리고 0.05 이상 가까울 때만 짝을 지어요. 확실하지 않으면 빼요.
- 크롭 생성(`crops_cube.py`)과 채점(`synth-eval.mjs`)이 같은 규칙을 써요.
- `train_cube.py`는 한 사진의 왼손과 오른손을 같은 쪽(학습 또는 검증)으로 나눠요.
- 렌더를 이어서 돌리다 같은 사진이 두 번 기록된 경우에는 마지막 줄만 써요.

**테스트.** `tools/test-match.mjs` 13개 케이스가 모두 통과했어요. 0·1·2개 검출, 교차한 손, 중복 검출, 잘못된 좌우 표시, 깍지, 완전히 같은 좌표, 가로 사진을 다뤄요.

**기존 데이터 감사.**

## 3. along 정의 통일
**좌표계.**
- 학습 라벨: 렌더 카메라 공간에서, 뼈 방향과 "관절에서 카메라로 가는 선" 사이의 cos이에요.
- fit: lift.js의 사진 좌표계를 써요. x와 y는 사진 속 위치이고 z는 시선 방향 깊이예요(약원근).
- 이 좌표계에서는 시선이 어디서나 z축이에요. 그래서 fit은 뼈의 z 성분과 라벨을 비교해요.

**확인한 내용.**
- 카메라 광선과 내적하는 방식도 시험했어요. 정답 라벨을 넣었을 때 seed10 오차가 15.44도에서 15.53도로 나빠져서 쓰지 않았어요.

**찾아서 고친 실제 버그.**
- 셀카 방향에서 `main.js`가 손을 뒤집는데, 이때 시선은 -z가 돼요. 그런데 +z로 비교하고 있어서 along의 부호가 반대였어요.
- lift가 꺼져 있을 때는 이제 큐브 항을 쓰지 않아요.

**테스트.** `tools/test-along.mjs`가 통과했어요.
- 라벨이 "카메라 쪽 선 기준 cos"과 정확히 같은지, 가운데·좌우·위아래·모서리에서 양손 모두 확인해요.
- 카메라 자체의 +z 축과는 가장자리에서 최대 0.51 차이 나요.
- 손을 뒤집은 좌표계(-z)에서도 값이 같아요.

**그 밖의 수정.**
- W_NAIL은 0 그대로예요.
- HaGRID 평가 도구에도 시선 방향(+z)을 넘기도록 고쳤어요. 이 값이 빠지면 fix 3 이후 큐브 항이 꺼지기 때문이에요.

## 4. 손바닥 옆면 충돌 누락
**원인.** `slabDepth`가 손바닥의 앞과 뒤만 봤어요. 그래서 손바닥 옆 가장자리에 들어온 손가락을 놓쳤어요. 재현 조건(손가락 공 중심 x=45mm, 반지름 8.5mm, 3.5mm 겹침)에서 0을 냈어요.

**수정.**
- 손바닥을 유한한 상자로 봐요. 가로는 lo부터 hi까지, 손목에서 손가락 뿌리까지의 20~90% 구간, 두께는 뒤부터 앞까지예요.
- 상대 손의 손가락 뼈는 캡슐로 보고, 캡슐과 상자 사이의 실제 거리를 재요.
- 상자 안에 들어간 경우에는 가장 가까운 면으로 빠져나간다고 계산해요.

**테스트.** `tools/test-collide.mjs`에 11개를 추가했고 모두 통과했어요. 앞, 뒤, 옆, 모서리 2개, 가장자리와 앞면에 딱 닿는 경우, 떨어진 경우, 양 끝이 밖에 있는데 손바닥을 관통하는 뼈, 손바닥 앞을 지나가는 뼈를 확인해요. 예전에 고친 원점 NaN, 앞뒤 순서 유지, 공백 너머로 보정이 새는 문제의 테스트도 통과했어요.

**떼어 놓기 결과(hpierce)를 옛/새 측정으로 교차 확인했어요.**
| | 손 포갬 | 깍지 |
|---|---|---|
| 옛 측정, 옛 처리 | 73 | 35 |
| 옛 측정, 새 처리 | 73 | 35 |
| 새 측정 | 75 | 33 |

- 손을 떼어 놓는 처리 결과는 그대로이고, 나빠지지 않았어요.
- 바뀐 것은 측정(검출)뿐이에요. **뚫림 자체가 해결된 건 아니에요.**

**20~90% 구간 따로 검토.** 0~100%로 넓히면 깍지가 45가 돼 한도 42를 넘어서 20~90%를 유지했어요. 손가락 뿌리 근처는 상대 손의 손가락 캡슐끼리 판정하는 부분이 맡아요.

## 남은 한계
- 서비스 워커 테스트는 데스크톱 Chromium에서만 했어요. 삼성 인터넷의 수명주기는 확인하지 못했어요.
- 동시에 두 요청이 들어올 때의 경합과 저장 공간 부족 상황은 재현하지 않았어요.
- 직전 버전보다 더 오래된 탭은 온라인에서 모델을 거부받아요. 페이지를 새로 고치면 돼요.
- 매칭에서 한 손만 그린 렌더는 비교할 다른 손이 없어서, 엉뚱한 검출을 거리만으로 걸러요. 화면 밖으로 나간 점이 있으면 보수적으로 제외해요.
- along은 약원근 근사라서, 사진 가장자리에서는 lift 오차가 더 커요.
- 뚫림은 측정만 정확해졌어요. 손가락끼리 엇갈리는 경우(깍지)는 아직 못 고쳤어요.
- 라이선스:
  - 자체 모델 3개는 학습 기록(manifest)과 소유자 라이선스 문구가 아직 없어요.
  - efficientdet_lite0 가중치의 라이선스 문구를 확보하지 못했어요. 추가하지 않은 기존 자산이에요.
  - Three.js MIT 전문은 vendor에 넣었어요. MediaPipe Apache 전문은 아직 없어요.

도돌이표 위험: 낮아요. 각 수정에 단위 테스트를 고정했어요. 다만 뚫림 수치는 측정 방식이 바뀌어서, 앞으로는 새 측정 기준(75/33)으로 비교해야 해요.
